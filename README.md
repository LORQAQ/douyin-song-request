# 抖音弹幕点歌 → B站自动播放（音乐模式）

观众在抖音直播间发一句 **「点歌 晴天」**，程序自动去B站找到最合适的视频、**只放声音**送进你的抖音直播伴侣。

- 面向 **抖音直播伴侣**（靠「系统声音」把音乐混进去，不用装虚拟声卡）
- 弹幕抓取有 **三条独立通道**，哪条通用哪条（HTTP 长轮询 / 浏览器插件转发 / 浏览器抓取）
- **选歌准**：自动排除翻唱、鬼畜、AI 翻调、切片，优先原版/官方投稿；热门歌走本地合集索引，
  每次点都命中同一个正确版本
- **歌单悬浮窗**：独立透明窗口，直播伴侣用「窗口捕获」加上去，观众能看到点歌列表
- 播放模式支持 **排队播放** 与 **立即打断**，控制台一键切换
- 带 **自动重试、音量自动校准（EBU R128）、撤销、播放历史、快捷键、一键体检**
- **直链过期自愈**：B站音频直链约 2 小时过期，程序会自动换新地址，不用你手动点
- 点歌有 **去重、冷却、每人配额、播放量/时长过滤**，防止被刷屏和点到奇怪视频

### 实测数据

| 指标 | 数值 |
|---|---|
| 启动到可用 | 254 ms |
| 点歌（命中本地索引） | **0.1~0.5 秒** |
| 点歌（联网搜索） | 3~5 秒 |
| 稳态内存 | RSS ≈ 130 MB / 堆 10~16 MB |
| 2000 条弹幕处理 | 5 ms |
| 连续 3 分钟 50 条/秒 | 内存 **零增长** |

## 一、快速开始（5 分钟）

```bat
:: 1. 安装依赖（只做一次）
npm install

:: 2. 启动
start.bat
```

> **最省事的用法**：桌面上的「抖音点歌」文件夹 → 双击 **① 启动全套**
> （会一次拉起：点歌程序 + 控制台 + 音乐播放页 + 歌单悬浮窗）
>
> 停止：同一个文件夹里的 **② 停止全套**

启动后自动打开控制台：**http://127.0.0.1:8787/**

然后在控制台里：

1. **直播设置 → 抖音直播间号**：填 `live.douyin.com/` 后面那串数字，点「保存并重连」
   （例如你直播间是 `https://live.douyin.com/7456814`，就填 `7456814`）
2. 等左上角「弹幕」变成 **绿色已连接**
3. 用小号在直播间发 `点歌 晴天` 试试

> 想先在电脑上试玩、不连直播间？`start.bat --mock`，然后在控制台「手动点歌」里输入歌名。

## 二、把音乐送进「直播伴侣」（关键一步）

直播伴侣没有浏览器源，所以要让观众听到音乐，办法是**让直播伴侣抓系统声音**：

```
B站音乐（本程序在浏览器里播放）
   ↓
Chrome 的音频输出 → 你的耳机/音箱（系统默认输出）
   ↓
直播伴侣 → 音频输入 → 选「系统声音 / 扬声器」
   ↓
观众听到音乐（顺便你自己也听到了，天然同步、零回声）
```

### 第 1 步：确认系统默认播放设备是你的耳机

```
右键任务栏喇叭图标 → 声音设置
→ 输出设备选你的耳机/音箱（比如「扬声器 (G20 Pro)」）
```

**不用装虚拟声卡。** 程序的声音直接去你的耳机，直播伴侣从那儿抓。

### 第 2 步：直播伴侣加一路音频

1. 打开抖音直播伴侣 → **添加素材 / 音频**
2. 音频来源选 **「系统声音 / 扬声器」**
3. 音量建议 60%~80%，别盖过你说话
4. 小号进直播间听一下：**人声正常、音乐正常、没有回声**

> ⚠️ **代价（要清楚）**：这种方式会把**耳机里的所有声音**都给观众，
> 包括游戏音效、微信/QQ 提示音。
> 如果你直播时会开这些软件，声音会一起进直播间。

### 想让「只有音乐进直播间」怎么办？

那就得用**虚拟声卡**把音乐单独抽成一路（[VB-CABLE](https://vb-audio.com/Cable/) 或 VoiceMeeter），
把 Chrome 的输出指到虚拟声卡，直播伴侣音频源选虚拟声卡的输出设备。

本程序**支持**这种方式（播放页右上角「🔈 输出设备」可以指定 `setSinkId`），
但**默认不启用**，因为配置麻烦、而且极容易出现回声。

> **回声的根本原因**：同一份音乐被送进耳机两遍以上。
> 用虚拟声卡时，务必保证整台机器上「侦听此设备」**只有一个设备是勾选的**
> （Windows 的监听 + 直播伴侣的监听 只能留一个）。

### 第 3 步：确认直播伴侣真的收到了音乐

打开音乐播放页 **http://127.0.0.1:8787/audio**，看左下角状态：

| 显示 | 含义 |
|---|---|
| 🟢 **直播伴侣可以读到音乐了** | 正常，观众能听到 |
| ⚪ 未播放 | 还没点歌，或者播放页没在播 |
| 🔴 音频中断，正在自动恢复 | 直链过期了，程序自己在换地址，等几秒 |

然后放一首歌（控制台「手动点歌」输入歌名），**看直播伴侣的音量条有没有跳动**。
跳了就说明通了。

### 第 4 步：自检

```bat
npm run doctor
```

会依次检查：Node/依赖、端口、B站搜索、B站 Cookie、直播间 roomId、弹幕通道能否收到数据。

## 三、弹幕从哪来（三种模式）

抖音的弹幕接口经常变动，所以这里做了三条通道，控制台「高级设置 → 弹幕来源」可以随时切换：

| 模式 | 说明 | 适用 |
| --- | --- | --- |
| `native`（默认） | 纯 Node 发 HTTP 长轮询拿弹幕，**不需要签名、不需要登录、不用装浏览器** | 正常情况下（实测 1 秒内就能收到弹幕） |
| `extension` | 装一个浏览器插件，把抖音页面自己那条连接的数据转给本程序 | native 万一被限制时的**保底方案** |
| `browser` | 用 Playwright 打开你的直播间页面，监听页面自己的 WebSocket | 不装插件时的备选；抖音会检测自动化，可能被限流 |
| `mock` | 不连抖音，手动输入测试 | 线下调试 / 排练 |

> **重要说明**：抖音的 WebSocket 弹幕接口对非官方客户端有设备信誉校验（服务端返回 `DEVICE_BLOCKED`），
> 实测换域名、换签名、带完整浏览器 Cookie、甚至在真实 Chrome 里新建连接都连不上，
> 所以本程序**不走 WebSocket 直连**，而是用官方页面同样在用的 HTTP 长轮询接口
> `/webcast/im/fetch/`——这条通道实测稳定可用（详见 `_probe_douyin/FINDINGS.md`）。
> `fallbackToBrowser` 默认关闭，需要自动降级可以打开。

### 插件模式怎么开

1. 在控制台「🚀 一键启动向导 → 可选」里点 **下载扩展 zip**（或访问 `http://127.0.0.1:8787/extension.zip`）
2. 解压到任意目录，Chrome 打开 `chrome://extensions` → 开启**开发者模式** → **加载已解压的扩展程序** → 选解压目录
3. 让 Chrome 打开你的直播间页面：`https://live.douyin.com/你的房间号`
   （如果你用直播伴侣的「浏览器」素材，它本身就是 Chrome 内核，同样能装扩展）
4. 控制台把弹幕来源切成 **插件转发**，点「重连弹幕」
5. 页面右下角会出现一个小窗，显示当前播放的歌曲和队列，可以直接「下一首」

### 音量自动校准（可选，推荐）

B站不同投稿的响度差异能到 10dB 以上——**实测四首常见歌的原始响度差了 11.2 dB**
（《晴天》-13.0、《稻香》-16.2、《孤勇者》-15.6、《漠河舞厅》-24.1 LUFS），
这就是「这首很小声、下首很吵」的原因。

开启后程序会用 ffmpeg 量一下每首歌的响度（只测 25 秒，**不到 1 秒出结果**），播放时自动补/减音量：
《漠河舞厅》自动 +6dB、《晴天》自动 -1dB，全部对齐到统一水平。控制台和播放页都会显示修正了多少。

怎么开启：

1. **程序会自动找 ffmpeg**，会依次尝试这些位置，并且**逐个验证真的能跑、带 loudnorm 滤镜**才使用：
   - `config.json` 里的 `loudness.ffmpegPath`
   - 项目 `tools` 目录
   - 环境变量 `FFMPEG_PATH`
   - 机器上已知的其它软件自带 ffmpeg（例如 `D:\oopz\ffmpeg.exe`）
   - 系统 `PATH`
2. 启动日志出现「**音量自动校准已启用（ffmpeg: ...）**」就是成功了。
3. 如果显示「没找到可用的 ffmpeg」：`winget install Gyan.FFmpeg`，或把 `ffmpeg.exe` 放进项目 `tools` 目录。

> 注意：不是所有叫 ffmpeg.exe 的都能用。比如 `D:\edge\ffmpeg.exe` 就不是 Windows 程序（跑不起来），
> 程序会自动跳过它并在调试日志里说明原因，不会因此崩溃。

想关掉：控制台点「音量自动校准」按钮，或 `config.json` 里 `loudness.enabled = false`。
想改目标响度：`loudness.targetLufs`（默认 `-14`，越小越响）。单次分析时长：`loudness.sampleSeconds`。

### 自动重试（不用观众再点一遍）

B站搜索偶尔会风控（HTTP 412）或超时。遇到这种**临时**失败，程序会把这首歌记下来，
45 秒后自动重试（最多 2 次），成功后直接排进队列。

控制台会显示「待重试的点歌」卡片，也可以点「立刻重试全部」。
永久失败（比如歌名太离谱搜不到）不会重试，避免白白占资源。

## 五、配置文件

首次启动会自动生成 `config.json`（和 `config.example.json` 同结构，改哪个都行）。
常用的几项：

```json
{
  "danmaku": {
    "source": "native",          // native / extension / browser / mock
    "webRid": "7456814",         // 你的直播间号
    "fallbackToBrowser": true    // native 失败自动降级
  },
  "trigger": {
    "keywords": ["点歌", "来一首", "想听"],
    "requireKeyword": true       // 必须带触发词才算点歌
  },
  "bilibili": {
    "cookie": "",                // 建议配（npm run cookie），几乎不会再撞 412 风控
    "minPlay": 10000,            // 最低播放量
    "minDurationSec": 60,        // 过滤太短的
    "maxDurationSec": 900,       // 过滤 1 小时循环那种
    "blacklistKeywords": ["翻唱", "伴奏", "钢琴", "鬼畜", ...]
  },
  "playback": {
    "mode": "queue",             // queue 排队 / interrupt 打断
    "audioMode": true,           // 只要音乐
    "useDirectStream": true,     // 纯音频直链；false 则用官方内嵌播放器
    "fallbackToEmbed": true,     // 直链失效自动回退
    "volume": 0.8
  },
  "filter": {
    "sameSongWindowMs": 900000,  // 同一首歌 15 分钟内不重复
    "perUserCooldownMs": 60000,  // 同一个人 60 秒内只能点一次
    "maxQueuePerUser": 3         // 一个人最多排 3 首
  },
  "launchPlayer": {
    "auto": false,               // 启动时自动拉专用播放器（默认关，手动开播放页就行）
    "deviceName": ""             // 留空 = 用系统默认输出（你的耳机）
  }
}
```

配置改了以后**重启程序**生效（少数项如音量、模式、触发词支持在控制台即时生效）。

## 六、B站 Cookie（可选，但强烈建议）

不配也能用，但配上以后**几乎不会再遇到 412 风控**（这是配 Cookie 的唯一主要好处）。

```bat
npm run cookie            :: 扫码登录版（推荐）——需要你手机扫码，之后自动完成
npm run cookie -- --guest :: 游客版——不用登录、不用操作，也能明显降低风控
```

扫码登录流程：脚本用**系统自带的 Chrome**（不用额外下载 Chromium）打开B站，
你用手机B站 App 扫码即可，**登录成功后脚本会自动检测**（不用按回车），
然后立刻验证 Cookie 是否有效，并告诉你登录的是哪个账号。

也可以手动：F12 → Application → Cookies → 拼成 `SESSDATA=xxx; bili_jct=xxx; ...`
粘进控制台「高级设置」，或直接写进 `config.json` 的 `bilibili.cookie`。

### ❗ 关于「Cookie 能提升音质」——这是错的，实测数据如下

| 同一个视频 | 无 Cookie | 游客 Cookie | 登录 Cookie |
| --- | --- | --- | --- |
| 【4K Hi-Res】稻香 | 210 kbps | 210 kbps | 210 kbps |
| 七里香 | 125 kbps | 125 kbps | 125 kbps |

**三条完全一样。** 原因：这个视频本身有三条音轨（66 / 102 / 210 kbps），
程序本来就按 `bandwidth` 排序取**最高**那条，匿名请求也能拿到。
所以网上说「配 Cookie 才有无损」在本项目里不成立——**别为了音质去折腾 Cookie**。

> 实测 Cookie 的真实价值：不配时连续搜索很快就开始返回 412；
> 配上之后连续搜索 8 首**全部成功、0 次风控**。

## 七、常见问题

**Q：控制台弹幕一直是灰色 / 连接失败？**
先 `npm run doctor` 看哪一步断了。直接连不上就把弹幕来源切成 **插件转发**（最稳），或 **浏览器抓取**。

**Q：音乐播放页没声音？**
1. 看播放页左上角圆点是绿还是红；红色说明连不上本地服务
2. 看是否停在「点一下这里开始播放」——点一下就行（Chrome 的自动播放限制）
3. 看 Windows 音量合成器里 Chrome 的输出设备是不是虚拟声卡
4. 直链音频失效会自动改用官方内嵌播放器，控制台会提示

**Q：直播伴侣里听不到音乐？**
- 虚拟声卡驱动装了吗？重启了吗？
- 直播伴侣那一路音频来源选对了吗？电平表有没有跳？
- 系统默认播放设备是不是被别的东西占走了？

**Q：点歌没反应？**
- 弹幕里必须带触发词（默认「点歌」「来一首」「想听」）
- 同一个人 60 秒内只能点一次、同一首歌 15 分钟内不重复（可在配置里放宽）
- 看控制台「最近弹幕」有没有收到那条弹幕；收到了却没点歌，就是触发词/过滤规则的问题

**Q：匹配到的视频不对？**
把「最低播放量」调高一些，或把不想要的词加进「弹幕屏蔽词」（例如 `翻唱,伴奏,钢琴,教程`）。
匹配逻辑是：标题吻合度 + 播放量 + 时长合理性 − 屏蔽词扣分，控制台队列里能看到「匹配分」。

### 选片规则：只要「第一手」+ 「完整版」

默认开启 `bilibili.firstHandOnly`，会**优先只用原唱/官方完整版**，翻唱二创一律重罚：

| 判定 | 依据 | 处理 |
| --- | --- | --- |
| **UP 主即歌手** | UP 主名字里就有歌手名（如「蔚蓝边际」发的《大家一起创羊羊》） | +45 分，最强一手信号 |
| **一手** | UP 主是**B站认证账号**；或标题/简介写明官方、原唱 | +30 分 |
| **时长＝完整度** | **2.5~7 分钟** +40；<45 秒 −80；<100 秒 −50；>30 分钟 −50 | 权重最高的硬指标 |
| **器乐/伴奏版** | 伴奏/纯音乐/笛子/钢琴/古筝/指弹/八音盒… | 直接排除 |
| **二创/翻唱/切片** | 翻唱、cover、改编、AI翻唱、鬼畜、串烧、remix、选秀、舞蹈、反应切片… | −80 分，不算一手 |
| **UP 主质量** | 粉丝数（1万粉≈+12，100万粉≈+36） | 加分 |
| **简介核对** | 无简介 −8；简介暴露器乐版 −60；简介不含歌名 −10 | 扣分 |

实测：10 首常见歌 **10/10 都选到完整版**（201~325 秒）。

> **为什么时长权重这么高？** 因为认证歌手入驻B站后**往往只发片段/宣传版**。
> 光看认证会把 1 分钟的片段排在 4 分钟的完整版前面，而观众点歌要的是整首歌。
> 实测把时长权重加上去之后，歌手发的 62 秒宣传片段（143 分）会输给完整版（255 分）。

### 实测：配了 Cookie 后搜索质量会变好

**这是个出乎意料的发现**——配上登录 Cookie 后，B站搜索接口返回的结果明显更准。

实测搜「大家一起创羊羊」：
- **配 Cookie**：原曲（歌手「蔚蓝边际」本人的投稿）稳定排在**第 1 名**（3/3 次）
- **不配 Cookie**：原曲时有时无

所以 Cookie 有**两个**好处：抗风控 + 搜索质量。不只是抗风控。

### ❗ 不要给搜索加「筛选参数」——实测反而更差

想过给B站搜索加「时长 1~5 分钟」「按播放量排序」这类参数来提高精度，
实测**全是负优化**：

| 搜索方式 | 结果 |
| --- | --- |
| **裸关键词** | ✅ 原曲排第 1 |
| + 时长筛选（duration=2） | ❌ 返回的全是**完全无关**的视频 |
| + 按播放量排序（order=click） | ❌ 原曲掉排名，混进不相干内容 |
| + 时长 + 分区音乐（tids=3） | ❌ 更糟 |

**结论：B站搜索就用裸关键词，多拉候选交给本地打分排序。**
程序已经这么做了（一次拉 30 条，本地按 20+ 个维度打分）。

### 那写个「改B站搜索规则」的插件有用吗？——没用

**B站搜索页的排序是给人类浏览用的，而程序不走搜索页。**

程序直接调 `api.bilibili.com/x/web-interface/search/type`。
所以在浏览器里改 DOM 排序、写油猴脚本改搜索页，
**对程序选片零影响**——数据来源是同一个接口，排序在我们自己手里。

真要干预，正确做法是调**本地打分的权重**（有 20 多个可调项），
而不是去改B站页面。

### 🎧 联网查原唱（重要：判断「谁是原唱」的唯一可靠办法）

光靠标题文本规则**猜不出**「告白气球的原唱是周杰伦」。
所以程序会先去**酷狗**查这首歌的原唱歌手和原曲时长，再用它来重排B站候选。

**选型是实测出来的，不是拍脑袋**：

| 接口 | 平均耗时 | 15 首命中率 | 说明 |
| --- | --- | --- | --- |
| **酷狗 songsearch v2** ✅ | **119ms** | **15/15** | 零签名，带 `IsOriginal` 原唱标记 |
| 咪咕 CMS | 177ms | 11/15 | 零签名，漠河舞厅查不到 |
| iTunes（country=hk） | 216~400ms | 15/15 | 有 429 限流，返回繁体 |
| MusicBrainz | 924ms | 排序不可靠 | 官方限速 1req/s，遇 503 |
| 网易云 | 263ms | **0/4** | 周杰伦版权下架，全是翻唱 |
| QQ音乐 | — | 不可用 | 接口返回 500 或空数组 |
| 酷我 | 88ms | 排序极差 | 晴天 TOP1 是 KTV 伴奏 |

> 两个坑都踩过：① 酷狗对空/乱码查询**不返回空数组**而是返回热门歌，
> 所以必须做歌名归一化校验；② 返回的歌手名可能是繁体，必须简繁归一。

拿到原唱后，用**两个硬指标**重排B站候选：

1. **标题/UP 名里出现原唱歌手** → UP 主本人发的 +55、标题署名 +25、没提到 −25
2. **时长接近原曲**（±6 秒 → +35，差 >60 秒 → −30）

实测效果（16 首，含此前所有选错的）：


> 另外两个「不吻合」的也合理：「孤勇者」选的是英雄联盟官方的**全球首唱版**（加长），
> 「突然的陀螺」是**歌手本人投稿**。
>
> 查询有 24 小时缓存 + 4 秒超时，**失败静默降级**到纯B站打分，
> 绝不会因为查不到原唱而点不了歌。想关掉：`bilibili.lookupOriginal = false`。

### 🎼 歌手合集定位（最可靠的「找原版录音」手段）

**这是目前最有效的一招。** 实测发现 B站 上有大量「歌手作品合集」多P投稿：

```
BV1aUaW6zEBg「周杰伦100首精选合集」→ 100 个分P，每个分P一首歌

   P4   224s  周杰伦 - 稻香

   P8   216s  周杰伦 - 告白气球

```

**为什么这招可靠**：分P 标题天然就是「歌手 - 歌名」格式，
时长也和原曲精确对应（实测 9 首歌**全部差 1~5 秒**），
比在散乱投稿里猜准得多。播放时带上 `?p=N` 即可。

**触发条件**（避免画蛇添足）：只在**散装候选不可靠**时才启用——
首选没有歌手署名、或时长明显不符、或B站标注为翻唱/改编。

实测直接调用 9/9 全部命中：

| 歌名 | 合集里找到 | 平台时长 | 偏差 |
| --- | --- | --- | --- |
| 夜曲 | 【经典】周杰伦全MV【200P】· P62 夜曲【6th 十一月的萧邦】 | 226s | 4s |
| 晴天 | 【周杰伦】50首精选合集 · P1 | 269s | 1s |

> 校验规则：分P 标题或合集标题里**必须出现歌手名**（防止别人合集里的翻唱被选中），

> 实测大回归（23 首）：**成功 23/23 · 歌手吻合 21/23 · 时长吻合 20/23 · 其中 3 首来自合集**。

### 🔄 B站标注可以修正音乐平台（实测发现）

**B站的标注比音乐平台准**，所以当两者冲突时以B站为准。实测证据：

「跳楼極」（BV1HyVtzPEM3）——

| 来源 | 说原唱是 | 对不对 |
| --- | --- | --- |
| 音乐平台（酷狗） | 王大龙 | ❌ 把B站搬运者的名字当成了歌手 |
| **B站简介** | **原曲《跳楼机》原唱 LBI利比** | ✅ 准确 |

B站那条视频的简介原文：原曲：《跳楼机》 原唱：LBI利比 混音：益辉 填词：蔚蓝边际 翻唱/视频：蔚蓝边际

所以程序会读B站标签/简介，两者不一致时**改用B站的歌手名**，
并把这个名字用于后续的歌手名补搜与合集查找（名字对了才找得到合集）。

> 两个防误修的约束（都踩过坑）：
> 1. **中文名优先**——B站简介有时写英文别名（「原唱：Jay」），
>    不能把平台给的「周杰伦」覆盖成「Jay」。
> 2. **需要多数印证**——至少 2 个候选的标注一致才采用，单个候选可能是错的。

### 📌 固定答案表（pins.json）—— 最准的一招

**实测发现 B站每次搜索返回的结果集都不一样**：同一首「大家一起创羊羊」，
有时能搜到歌手本人的投稿（148s，蔚蓝边际），有时前 20 条全是切片和舞蹈视频。
**这种情况任何算法都救不了**，所以给主播一个「记住正确答案」的开关。

在项目根目录建 `pins.json`（已被 `.gitignore` 忽略，只在本机生效）：

```json
{
  "_说明": "键=点歌文本，值=BV号 或 {bvid, page}。删掉某行就恢复自动搜索。",
  "大家一起创羊羊": "BV1M8gnzSEeh",
  "跳楼極": "BV1HyVtzPEM3",
  "跳楼机": "BV1oVQPY3EGJ",
  "某首多P合集里的歌": { "bvid": "BV1xxx", "page": 7 }
}
```

**两级匹配，精确优先**：

1. **精确**（只做繁简归一）——所以「跳楼極」和「跳楼机」可以各占一条，
   不会互相覆盖（它们是两首不同的歌：前者是改编，后者是原曲）。
2. **兜底**（歌名异体归一）——「跳楼极」「跳樓極」这类非标准写法会落到最近的键上。

命中的歌曲会**跳过整条搜索流程**，直接用你指定的视频，
日志里显示 `📌 使用固定答案：…`。想关掉：`bilibili.usePins = false`。

### ⚠️ 自动匹配的天花板（重要）

**自动搜索再准也只是「猜」**，有两个绕不过去的限制：

1. **原唱经常搜不到**——热门歌在B站大量被版权下架，搜出来的全是二创。
2. **搜索排名不由我们控制**——B站给「反应/切片」类高互动内容很高权重。
   实测搜「大家一起创羊羊」时，歌手本人（蔚蓝边际）的**原曲排不进前 30 条**，
   出来的全是别人直播间的切片。程序只能从拿到的那批结果里挑。

**想 100% 放对某个视频，用这个办法：**

直接让观众/主播把B站链接或 BV 号发出来，程序**不搜索、直接播那个视频**：

```
点歌 BV1RMGKzsEEf
点歌 https://www.bilibili.com/video/BV1RMGKzsEEf
点歌 av18026414
```

这是唯一能保证「放的就是想要的那个」的方式。推荐在直播间公告里写一句：
**「想点特定版本请直接发B站链接或 BV 号」**。

> 想放宽自动匹配（冷门歌只有翻唱版）：
> `bilibili.firstHandOnly` 设为 `false`。

**Q：会不会点到不能播的视频？**
会有极少数视频禁止外嵌播放，这时播放页会报错并自动跳下一首（`playback.skipOnError`）。

**Q：为什么音频要经过本程序转发，会不会卡？**
B站音频 CDN 校验 Referer，浏览器从 `127.0.0.1` 直接播会 403，所以由本程序带上正确请求头转发（支持 Range 断点续传，边下边播）。
原生播放器就是直接播 CDN 地址，所以比直连多一跳，但都在本机内网，实测无感知；如果你更在意稳定性，可以把「播放方式」切成内嵌播放器（画面会被隐藏，只出声）。

**Q：日志里提示「通过 WBI 备用通道搜索成功」是什么？**
B站搜索接口偶发 412 风控，程序会自动换一条签名接口重试成功。配了 Cookie 就不太会出现。
如果两条都失败，这首歌会进入「待重试」列表，45 秒后自动再试，不用观众重新点。

**Q：为什么有的歌听起来特别小声/特别吵？**
B站不同投稿的响度差异很大。开启「音量自动校准」（控制台开关，需要 ffmpeg，见上文）后会自动平衡到统一水平。
不想装 ffmpeg 的话，也可以自己用 Windows 音量合成器调个折中值。

**Q：控制台显示「待重试的点歌」是什么？**
B站搜索被风控或超时导致的临时失败。程序会自动重试，也可以点「立刻重试全部」。
反复失败通常是歌名太离谱（比如弹幕发的是整句话），可以调触发词或看「最近弹幕」确认。

**Q：一天播下来程序会不会越跑越卡？**
内置了 LRU 缓存（搜索结果/视频信息/音频直链都有条数上限）、队列与历史条数上限、
每 10 分钟一次内存采样。如果提示内存偏高，重启一次程序即可（建议每天开播前重启）。

### 性能与内存（实测数据）

真实直播间实测（107 条弹幕 / 526 条消息，运行 48 秒）：

```
平均 CPU 占用   0.55%
堆内存          11 MB
RSS             85 MB
```

微基准（`npm run test:bench`）：

| 项目 | 实测 |
| --- | --- |
| 解一帧混合消息（40 条，弹幕 : 其它 ≈ 1:2） | **91 µs**（不做优化是 181 µs，**省 50%**） |
| 解一帧纯弹幕（20 条） | 115 µs |
| 引擎处理一条弹幕（含状态广播） | 7.4 µs |
| getState 序列化 | 2.2 µs |
| 10000 条弹幕 / 7500 次点歌（压力测试） | 4.1 秒处理完，堆内存只涨 16.6 MB |

做了这些优化：

1. **跳过非弹幕消息的解压**（最大头）。真实房间里进场/点赞/礼物消息的数量是弹幕的 2~4 倍，
   而点歌只需要 `WebcastChatMessage`。实测 526 条消息里只有 107 条是弹幕。
   需要进场事件时把 `danmaku.decompressOthers` 设为 `true`。
2. **varint 解码不再用 BigInt**。改成纯数字快路径（4 字节以内），只有雪花 ID 这种
   超过 2^53 的大数才回退 BigInt 并转字符串，返回值类型和以前完全一致（有测试守着）。
3. **状态广播节流**。弹幕高峰期每秒序列化十几次 9KB 的 state 是纯浪费，
   现在 250ms 合并一次（`playback.stateBroadcastMs`），播放切换等关键节点仍然立即推送。
4. **弹幕缓存可控**：`playback.recentChatsSize`（默认 30），超长弹幕截断到 200 字。
5. **搜索/详情/音频直链缓存全部用 LRU 限条**，历史与队列也有上限。

## 九、技术要点与已验证结论

这些结论都是在本机实测得到的（完整证据见 `_probe_douyin/FINDINGS.md`），不是猜的：

| 验证项 | 结果 |
| --- | --- |
| **抖音 HTTP 长轮询** `/webcast/im/fetch/?resp_content_type=protobuf` | ✅ **可用**：纯 Node、不需要 signature/X-Bogus/登录，实测 1 秒内拿到 40 条消息、8 条真实弹幕 |
| 抖音 WebSocket 直连 `webcast*.douyin.com/webcast/im/push/v2/` | ❌ `HTTP 200 + handshake-msg: DEVICE_BLOCKED`（ws 库只表现为 close 1006）；换域名/签名/完整 Cookie/真实 Chrome 内新建连接全部失败 |
| `signature` 的真实算法 | 是 `byted_acrawler.frontierSign()` 产出的 16 字符 X-Bogus，不是网上流传的 98 字符 md5 串；**HTTP 通道完全不校验它** |
| web_rid → roomId | ✅ 用 `/webcast/room/web/enter/?web_rid=`（HTML 里已经抓不到 roomId 了） |
| 弹幕 protobuf 字段 | `Message{1:method, 2:payload(gzip), 3:msgId}`（payload 在 **field2**）；`PushFrame.payload` 本身也是 gzip |
| 真实 Chromium 打开播放页并出声 | ✅ `currentTime` 正常前进（`node scripts/browser-check.js`） |
| `search/type?search_type=video` 搜索 | ✅ 可用（带 Chrome UA + Referer，偶尔 412 风控） |
| `wbi/search/type` WBI 签名备用通道 | ✅ 可用，主通道被风控时自动顶上 |
| `player/playurl (fnval=16)` 取 DASH 音频 | ✅ 可用（`mp4a.40.2`） |
| 音频直链直接用浏览器播 | ❌ **403**，CDN 校验 Referer，必须走本机代理 |
| 本机代理转发音频（含 Range） | ✅ 206 分段正常，`<audio>` 能边下边播 |

- **弹幕链路**：`room/web/enter` 拿 roomId → 循环 `im/fetch`（带上次的 cursor）→ protobuf + gzip 解码 → 弹幕文本
- **选片打分**：标题吻合度（完全一致/开头/包含/覆盖率）+ 播放量对数分 + 时长区间 + 标题紧凑度 − 黑名单/教程类扣分
- **降级链**：`native` → `browser` → `extension`（可配置），任何一步失败都能继续用

### 抖音弹幕协议：为什么不用 WebSocket

这次的实测（`_probe_douyin/FINDINGS.md`，含 18 个可复现脚本）推翻了几条流传很广的说法：

1. **WebSocket 直连已不可用**。服务端对非官方客户端做设备信誉判定，返回
   `HTTP 200 + handshake-msg: DEVICE_BLOCKED + handshake-status: 415`
   （`ws` 库只表现为 `close 1006`，不看 `unexpected-response` 根本查不出原因）。
   换域名、换 signature、带完整 30 个浏览器 Cookie、甚至**在真实 Chrome 页面里 `new WebSocket(同一 URL)`**
   都失败，而同一个页面抖音自己的连接却正常——所以这不是参数或算法问题。
2. **网上那套 98 字符 `signature` 算法是错的**。官方前端实际是把
   `md5(websocket_key 串)` 作为 `X-MS-STUB` 交给 `byted_acrawler.frontierSign()`
   得到 16 字符的 `signature`（即 X-Bogus）。
3. **HTTP 长轮询完全不校验 signature**，这才是可用通道：
   `GET https://live.douyin.com/webcast/im/fetch/?resp_content_type=protobuf`，
   循环带上一次响应里的 `cursor` 即可持续收弹幕，不需要登录。
4. **roomId 已经不在直播间 HTML 里**（页面改成 RSC 流式渲染），要调
   `/webcast/room/web/enter/?web_rid=xxx`，必要时先访问页面拿 `ttwid` 再重试。
5. **protobuf 字段号**：`Message{1:method, 2:payload(gzip), 3:msgId}`（payload 在 field2）；
   `PushFrame.payload` 本身也是 gzip，两层都要解。
